# План разработки AI-торгового бота для Hyperliquid

**Стек:** Python 3.13, Async SQLAlchemy, PostgreSQL, Alembic, FastAPI, uv, Pydantic, Pydantic Logfire, Pydantic AI, CatBoost, Docker Compose, React, httpx, websockets.

**Выбор MVP:** BTC perpetual, таймфрейм 1h.

**Решение 2026-11-17: testnet не используется, сразу mainnet.** Риск компенсируется так:

- торговля на основном аккаунте (решение 2026-11-17: субаккаунт не используется); худший случай ограничивают лимит номинала 20 USDC, isolated-маржа 2x и обязательный биржевой stop;
- на этапах 6–8 каждый ордер подтверждается вручную в CLI, размер ордеров минимальный (~10–15 USDC);
- для технических тестов лимит номинала снижен до 20 USDC (`max_position_notional_usdc`), к 200 USDC — только после этапа 14;
- ключ API-кошелька хранится отдельно (`.env.mainnet.secrets`) и доступен только торговому процессу; коллектор его не получает;
- перед автоматикой — обязательный `SHADOW`.

**Дата проверки документации Hyperliquid:** 17 ноября 2026 г.

## 1. Общий подход

Порядок разработки должен быть следующим:

> **Сначала надёжный торговый контур → затем риск-менеджмент и восстановление после сбоев → затем CatBoost → затем ограниченный запуск на реальные деньги.**

Модель не должна напрямую возвращать команду «купить» и отправлять ордер. Правильная цепочка:

```text
Рыночные данные
      ↓
Признаки
      ↓
CatBoost: вероятности up / down / flat
      ↓
Торговая политика: желаемая позиция
      ↓
Risk engine: разрешено ли торговать и каким объёмом
      ↓
Execution engine: создание и контроль ордеров
      ↓
Hyperliquid
      ↓
Сверка фактического состояния с локальной БД
```

### Отношение к бэктесту

Исторический бэктест торговой стратегии в этот план не включён по требованию проекта. При этом важно учитывать: бэктест не доказывает будущую прибыльность, но может обнаруживать утечки данных, ошибки в сигналах и неучтённые издержки.

Вместо него предусмотрены:

1. Проверка качества модели на более позднем участке данных — без симуляции торговли и расчёта гипотетического PnL.
2. Минимальный mainnet вместо testnet: отдельный субаккаунт, ордера минимального размера, ручное подтверждение каждого ордера.
3. Mainnet shadow-режим с реальными данными, но без ордеров.
4. Тестирование сбоев.
5. Минимальный реальный запуск с жёсткими лимитами.

Такой путь не полностью заменяет проверку экономики стратегии, поэтому масштабирование капитала должно быть особенно осторожным.

Компромисс без симуляции торговли: на этапе проверки модели считать **среднюю будущую доходность по сигналам минус издержки** (комиссия, спред, проскальзывание, funding). Это не бэктест с PnL-кривой, а sanity-check, что сигналы в принципе перекрывают издержки.

## 2. Допущения для первой версии

Чтобы не распыляться, MVP фиксируется со следующими ограничениями:

- только perpetual futures, без спота, vaults и HIP-3;
- один рынок: **BTC**;
- один аккаунт или выделенный субаккаунт;
- один таймфрейм: **1 час** (горизонт прогноза фиксируется на этапе 0, кандидат — 4 свечи);
- решения только по закрытым свечам;
- изолированная маржа и минимальное плечо;
- максимум одна позиция по инструменту;
- без усреднения, мартингейла и пирамидинга;
- без автоматического разворота из long сразу в short;
- вход через IOC-ордер с ограничением допустимой цены;
- закрытие через `reduceOnly`;
- биржевой защитный stop-loss;
- один активный торговый процесс;
- FastAPI и React — только управление и мониторинг;
- до появления React управление идёт через CLI (`status`, `pause`, `cancel-all`, `flatten`, `kill`) поверх тех же сервисов;
- уведомления оператору — через Telegram-бота;
- Pydantic AI не участвует в принятии торговых решений.

Поддержка нескольких рынков, портфеля стратегий и автоматического переобучения добавляется позже.

## 4. Этап 0. Зафиксировать торговую и риск-спецификацию

До написания кода необходимо письменно определить правила.

### 4.1. Рынок и решения

- Какой инструмент используется.
- Какой выбран таймфрейм.
- Через сколько свечей оценивается результат прогноза.
- Разрешены ли long и short.
- Когда позиция удерживается.
- Когда закрывается.
- Допускается ли повторный вход сразу после закрытия.
- Что происходит, если новый сигнал совпадает с уже открытой позицией.

Для MVP предлагается следующая логика:

```text
BUY  → открыть long только если позиции нет
SELL → открыть short только если позиции нет
HOLD → не открывать новую позицию
EXIT → закрыть существующую позицию
```

Автоматический переворот позиции в первой версии запрещён.

### 4.2. Лимиты

В конфигурации должны быть явно заданы:

- максимальный риск на сделку;
- максимальный размер позиции в базовом активе;
- максимальный номинал позиции в USDC;
- максимальное плечо;
- максимальный убыток за день;
- максимальный убыток за неделю;
- максимальное число сделок за период;
- минимальное расстояние до stop-loss;
- максимально допустимый спред;
- максимально допустимое проскальзывание;
- максимальный возраст рыночных данных;
- максимальное время неопределённого статуса ордера;
- запрет торговли при превышении любого лимита.

### 4.3. Режимы работы

```text
DISABLED       — никаких торговых действий
TESTNET        — торговля только на testnet
SHADOW         — реальные данные, сигналы сохраняются, ордеров нет
LIVE_PAUSED    — реальный аккаунт, новые входы запрещены
LIVE_ENABLED   — реальная торговля разрешена
```

Переход в `LIVE_ENABLED` должен быть ручным, подтверждённым и записанным в аудит. После перезапуска бот не должен самостоятельно переходить в этот режим.

**Критерий готовности:** на любой сигнал можно однозначно ответить, какое действие разрешено, каким объёмом и при каких условиях оно должно быть отклонено.

## 5. Этап 1. Подготовить проект и конфигурацию

### 5.1. Базовая инфраструктура

- Проект и lock-файл управляются через uv.
- Все зависимости фиксируются по версиям.
- Настройки загружаются через Pydantic Settings.
- SQLAlchemy используется в async-варианте.
- Alembic настраивается сразу, а не после появления production-БД.
- Добавляются тесты, линтер и проверка типов.
- Docker Compose используется для локального окружения (PostgreSQL), но приложение не должно зависеть от особенностей конкретного container runtime.
- Резервное копирование PostgreSQL (`pg_dump` по расписанию) настраивается сразу, восстановление из бэкапа проверяется до первых реальных данных.

### 5.2. Разделение окружений

Для testnet и mainnet должны быть разные:

- базы данных;
- API-кошельки;
- секреты;
- конфигурационные файлы;
- визуальные обозначения в интерфейсе;
- разрешения на запуск.

Официальная документация предоставляет [Python SDK](https://github.com/hyperliquid-dex/hyperliquid-python-sdk) и отдельный testnet URL. См. [описание API](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api).

Следует сделать защиту от ошибочной конфигурации:

```text
ENVIRONMENT=testnet
HYPERLIQUID_NETWORK=testnet
TRADING_MODE=testnet
```

Если значения противоречат друг другу, приложение должно завершать запуск с ошибкой. Для mainnet дополнительно требуется явный флаг подтверждения.

### 5.3. Логирование

В Logfire нельзя отправлять:

- приватные ключи;
- подписанные payload целиком, если они содержат чувствительные данные;
- секретные заголовки;
- токены доступа к панели;
- переменные окружения без фильтрации.

Для каждой операции нужен `correlation_id`, связывающий:

```text
свечу → признаки → прогноз → решение → риск-проверку
→ ордер → ответ API → fills → изменение позиции
```

**Критерий готовности:** приложение невозможно случайно запустить с testnet-ключом и mainnet URL или наоборот; секреты не появляются в логах.

## 6. Этап 2. Спроектировать базу данных

### 6.1. Рынки и метаданные

Таблица `markets`:

- `network`;
- `dex`;
- `coin`;
- `asset_id`;
- `sz_decimals`;
- параметры маржи и плеча;
- время последнего обновления метаданных;
- исходный `meta` в JSONB.

Asset ID нельзя жёстко прописывать в коде: для perpetuals он определяется через `meta`, а идентификаторы mainnet и testnet могут различаться. См. [Asset IDs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/asset-ids).

### 6.2. Рыночные данные

Таблица `candles`:

- рынок;
- интервал;
- время открытия и закрытия;
- OHLCV;
- количество сделок;
- признак закрытия свечи;
- источник: REST или WebSocket;
- время получения.

Уникальный ключ:

```text
(network, dex, coin, interval, open_time)
```

Таблица `market_context_snapshots`:

- mark price;
- oracle price;
- funding;
- open interest;
- время биржи;
- время получения.

Таблица `bbo_snapshots` или агрегированные данные стакана создаются только при наличии реальной потребности. Для часового бота не обязательно сохранять каждое изменение стакана.

### 6.3. Модель и сигналы

Таблица `model_versions`:

- версия;
- хеш файла модели;
- список и версия признаков;
- параметры формирования target;
- период обучения;
- метрики;
- статус: `candidate`, `shadow`, `active`, `retired`;
- дата создания и активации.

Таблица `feature_snapshots`:

- время;
- рынок;
- версия признаков;
- значения в JSONB;
- хеш входных данных;
- последняя использованная закрытая свеча.

Таблица `signals`:

- вероятности классов;
- решение политики;
- причина отказа, если сигнал отклонён;
- версия модели;
- версия торговой политики;
- ID признаков;
- время формирования;
- горизонт прогноза;
- фактический результат, который можно заполнить после наступления горизонта.

### 6.4. Торговля

`order_intents` — намерение создать ордер ещё до обращения к бирже.

Таблица `orders`:

- внутренний UUID;
- `cloid`;
- `oid`;
- nonce;
- рынок;
- сторона;
- цена и размер;
- тип ордера;
- `reduce_only`;
- текущий статус;
- сырые ответы API;
- время отправки и последнего обновления.

Дополнительно:

- `order_events` — все изменения статусов с дедупликацией;
- `fills` — фактические исполнения, комиссии и closed PnL;
- `position_snapshots` — история состояния позиции;
- `account_snapshots` — equity, margin, withdrawable и другие показатели;
- `funding_events` — фактические платежи финансирования.

### 6.5. Управление

Необходимы таблицы:

- `risk_limits`;
- `bot_state`;
- `heartbeats`;
- `audit_log`;
- `reconciliation_runs`;
- `reconciliation_differences`.

Для денежных значений использовать `Decimal` и PostgreSQL `NUMERIC`. Исходные строки API сохранять в JSONB, чтобы не потерять точное представление биржи.

### 6.6. Инкрементальное создание схемы

Описанная схема — целевая. Миграции Alembic добавляются по мере надобности, а не все таблицы сразу:

1. Этап 2 (БД v1): `markets`, `candles`, `market_context_snapshots`, `bot_state`, `audit_log`, `heartbeats`.
2. Этап 6: `order_intents`, `orders`, `order_events`, `fills`, `position_snapshots`, `account_snapshots`, `funding_events`.
3. Этап 7: `reconciliation_runs`, `reconciliation_differences`.
4. Этап 8: `risk_limits`.
5. Этапы 10–11: `model_versions`, `feature_snapshots`, `signals`.

**Критерий готовности:** повторная обработка одного WebSocket-события не создаёт второй fill или второе изменение позиции; любой ордер можно восстановить по истории событий.

## 7. Этап 3. Сделать read-only интеграцию с Hyperliquid

Сначала система не выполняет никаких подписанных действий.

### 7.1. Собственный адаптер поверх SDK

Официальный SDK фиксируется по версии и скрывается за собственным интерфейсом:

```python
class HyperliquidGateway:
    async def get_meta(...): ...
    async def get_candles(...): ...
    async def get_account_state(...): ...
    async def get_open_orders(...): ...
    async def get_fills(...): ...
    async def place_order(...): ...
    async def cancel_order(...): ...
```

Вся остальная система не должна зависеть от структур SDK. Это упростит обновление SDK, тестирование и обработку ошибок.

Если используемая версия SDK блокирует event loop, её вызовы необходимо изолировать в подходящем worker/executor либо использовать отдельный синхронный execution-процесс. Это проверяется практически на выбранной версии, а не предполагается заранее.

**Рекомендуемый вариант:** официальный SDK синхронный (`requests` и поток `websocket-client`). Поэтому:

- info-запросы и WebSocket — собственный тонкий async-клиент на `httpx` и `websockets` (это обычный JSON);
- SDK (с зафиксированной версией) используется только для подписи действий (`hyperliquid.utils.signing`) и построения wire-формата ордеров;
- подпись — чистая CPU-операция без сети, её можно вызывать из async-кода напрямую;
- совместимость подписи проверяется на mainnet безопасным действием (`updateLeverage` для BTC isolated — не двигает средства и не открывает позиций) до начала этапа 6.

### 7.2. Первые запросы

- `meta`;
- `metaAndAssetCtxs` или соответствующие актуальные info-запросы;
- `candleSnapshot`;
- `allMids`;
- `clearinghouseState`;
- `openOrders`;
- `userFillsByTime`;
- `userRateLimit`.

Для пользовательских данных передаётся адрес основного аккаунта или субаккаунта. Адрес API-кошелька используется для подписи, а не как адрес торгового аккаунта. Документация отдельно описывает эту распространённую ошибку: [Nonces and API wallets](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/nonces-and-api-wallets).

### 7.3. Нормализация инструментов

Необходимо реализовать:

- получение `asset_id` из актуальных метаданных;
- обновление метаданных по расписанию;
- округление размера по `szDecimals`;
- проверку цены по правилам significant figures и decimal places;
- минимальный номинал;
- сохранение исходных и нормализованных значений.

Цены Hyperliquid имеют ограничения по значащим цифрам и количеству десятичных знаков, а размеры округляются согласно `szDecimals`. См. [Tick and lot size](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/tick-and-lot-size).

Округление должно быть безопасным:

- размер позиции — в меньшую сторону, чтобы не превысить риск;
- цена входа — с учётом стороны и максимально допустимого проскальзывания;
- защитная цена — так, чтобы случайно не ослабить ограничение риска.

### 7.4. Исторические свечи для обучения

`candleSnapshot` предоставляет только последние 5000 свечей (для 1h это около 208 дней), поэтому сбор собственных данных нужно запустить как можно раньше. См. [Info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint).

Поэтому сразу после read-only интеграции идёт отдельный шаг — **коллектор данных** (раздел 8.5): он запускается и работает постоянно, пока строится торговый контур.

Если этого недостаточно для обучения:

- подключить дополнительный источник исторических данных: архив Hyperliquid в S3 (requester-pays; доступность и формат проверить на момент подключения) и, как вспомогательный, BTCUSDT 1h с крупной CEX;
- записывать происхождение каждой записи;
- проверять совпадение источников на пересекающемся периоде;
- не смешивать данные без контроля часовых поясов, символов и правил построения свечей.

**Критерий готовности:** бот корректно получает метаданные, свечи, состояние аккаунта и ордера; asset ID не захардкожены; округление проходит тесты на граничных значениях.

## 8. Этап 4. Реализовать потоковые данные и восстановление пропусков

### 8.1. Подписки

Для MVP:

- `candle`;
- `trades`, если нужны;
- `bbo` для спреда и оценки исполнения;
- `activeAssetCtx` для funding, open interest, mark/oracle price;
- `orderUpdates`;
- `userFills`;
- `userFundings`;
- `userNonFundingLedgerUpdates`.

Документация требует корректно обрабатывать отключения WebSocket: после переподключения могут прийти snapshot-данные, а пропущенные сведения можно восстановить через info-запросы. См. [WebSocket](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket) и [Subscriptions](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions).

### 8.2. Механика обработки

1. Подключиться.
2. Подписаться заново.
3. Принять и пометить snapshot.
4. Дедуплицировать уже сохранённые события.
5. Выполнить REST-запрос для восстановления возможного разрыва.
6. Только после этого перевести поток в состояние `healthy`.

Нельзя просто игнорировать все сообщения с `isSnapshot: true`: после сбоя в них могут находиться пропущенные события.

### 8.3. Закрытые и незакрытые свечи

В БД можно обновлять текущую свечу, но для модели использовать её только после закрытия.

У каждого feature snapshot должно быть поле:

```text
data_available_at
```

Оно показывает, когда информация реально стала доступна боту. Это поможет не использовать значения незакрытой свечи или ещё не полученные данные.

### 8.4. Heartbeat и устаревание

Отдельно отслеживаются:

- время последнего сообщения WebSocket;
- биржевое время последнего события;
- локальное время получения;
- время последней успешной REST-сверки;
- задержка обработки очереди.

При превышении порога:

- запретить новые входы;
- не считать отсутствие сообщений отсутствием рыночных изменений;
- инициировать переподключение и сверку;
- сохранить существующие биржевые защитные ордера.

### 8.5. Коллектор данных — запуск как можно раньше

Первая версия этого этапа — отдельный долгоживущий процесс-коллектор, который не зависит от торговой части:

- REST backfill последних 5000 часовых свечей BTC при старте;
- подписки `candle` и `activeAssetCtx` (funding, OI, mark/oracle price);
- переподключение и восстановление пропусков по алгоритму 8.2;
- идемпотентная запись (upsert по уникальному ключу);
- heartbeat в БД и простой CLI-отчёт о пропусках.

Коллектор запускается сразу после готовности и работает постоянно, пока разрабатываются этапы 5–9. Пользовательские подписки (`orderUpdates`, `userFills` и т. д.) добавляются позже, на этапе execution.

**Критерий готовности:** после принудительного разрыва соединения бот восстанавливает пропуски, не дублирует fills и не разрешает вход на устаревших данных.

## 9. Этап 5. Настроить API-кошельки, подписи и nonce

### 9.1. Безопасность кошельков

- Основной приватный ключ на сервер не помещать.
- Для торговли использовать отдельный API/agent wallet.
- Для testnet и mainnet использовать разные ключи.
- Для каждого независимого торгового процесса — отдельный API-кошелёк.
- При использовании субаккаунтов желательно выделять отдельный кошелёк на каждый процесс/субаккаунт.
- Старые адреса API-кошельков повторно не использовать: документация предупреждает о pruning nonce-состояния и возможности неожиданного replay после повторного использования.

Ключи хранятся в secret manager или как минимум в отдельном секрете окружения с ограниченным доступом. Их нельзя хранить в React, PostgreSQL, Git или обычных логах.

### 9.2. Ограничение разрешённых действий

В execution-слое создаётся allowlist:

```text
order
cancel
cancelByCloid
updateLeverage
scheduleCancel
```

Функции вывода средств, переводов и управления кошельками в торговый сервис не добавляются.

### 9.3. Nonce manager

Nonce ведутся по подписывающему кошельку. Поэтому один API-кошелёк, одновременно используемый несколькими процессами или субаккаунтами, создаёт риск коллизий.

Отдельный компонент должен:

- выдавать уникальный nonce;
- использовать миллисекундную временную основу;
- быть защищённым блокировкой;
- хранить последний выданный nonce;
- после перезапуска брать `max(current_time_ms, last_nonce + 1)`;
- не позволять двум экземплярам execution engine работать одновременно;
- контролировать синхронизацию системных часов.

Для гарантии единственного торгового процесса дополнительно можно использовать PostgreSQL advisory lock, но это не отменяет правила «один процесс — один API-кошелёк».

**Критерий готовности:** перезапуск и попытка параллельного запуска не приводят к повторному nonce или двум активным execution engine.

## 10. Этап 6. Построить execution engine без AI

До подключения модели все действия проверяются вручную созданными тестовыми сигналами (через CLI).

### 10.0. Минимальный guard с первого дня

Полный risk engine появляется на этапе 8, но execution engine с самого начала не может отправить ордер без жёстких проверок:

- режим работы допускает торговлю в этой сети;
- размер не превышает `max_position_size`;
- номинал не превышает `max_notional_usdc`;
- закрывающий ордер всегда `reduceOnly`;
- разворот позиции запрещён;
- не больше одной позиции по инструменту.

Биржевой защитный stop-loss тестируется уже на этом этапе, а не только на этапе 8.

### 10.1. Жизненный цикл ордера

```text
CREATED
  ↓
RISK_APPROVED
  ↓
PERSISTED
  ↓
SIGNED
  ↓
SENT
  ↓
RESTING / PARTIALLY_FILLED / FILLED
        / CANCELED / REJECTED / UNKNOWN
```

Отдельный статус `UNKNOWN` обязателен. Например, соединение оборвалось после отправки, но до получения ответа. В этот момент нельзя считать, что ордер точно не принят.

### 10.2. Алгоритм отправки

1. Создать внутренний `order_intent`.
2. Проверить риск.
3. Сохранить намерение в PostgreSQL.
4. Сгенерировать уникальный `cloid`.
5. Нормализовать цену и размер.
6. Получить nonce.
7. Подписать действие.
8. Отправить запрос.
9. Сохранить полный ответ.
10. Дождаться подтверждений через API/WebSocket.
11. Обновить состояние.
12. При неопределённости запустить reconciliation.

Hyperliquid поддерживает 128-битный клиентский идентификатор `cloid`. Внутри бота он должен быть обязательным, с уникальным индексом в БД. См. [Exchange endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint).

### 10.3. Обработка ответа

Нельзя проверять только HTTP 200 или верхнеуровневый `status: "ok"`. Ошибки конкретных ордеров могут находиться внутри массива результатов; документация также описывает ошибки, относящиеся ко всему batch. См. [Error responses](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/error-responses).

Нужно отдельно обрабатывать:

- `resting`;
- `filled`;
- частичное исполнение;
- вложенный `error`;
- отказ по марже;
- отказ по tick size;
- отказ `reduceOnly`;
- отсутствие ликвидности;
- сетевой таймаут;
- ограничение запросов;
- неизвестный формат ответа.

Неизвестный формат нельзя незаметно игнорировать: необходимо остановить новые действия и записать ошибку интеграции.

### 10.4. Повторная отправка

При таймауте запрещено сразу повторять ордер.

Правильный порядок:

1. Найти ордер по `cloid` через `orderStatus`.
2. Проверить `openOrders`.
3. Проверить fills.
4. Проверить позицию.
5. Только после этого решить, безопасен ли повтор.

### 10.5. Типы ордеров в MVP

- **Вход:** IOC с максимальной/минимальной допустимой ценой.
- **Выход:** IOC `reduceOnly`.
- **Защитный stop:** биржевой trigger-ордер.
- **GTC и ALO:** добавить позже, когда надёжно работает базовый жизненный цикл.

Противоположный ордер без `reduceOnly` может не просто закрыть позицию, а открыть позицию в другую сторону. Поэтому в MVP все закрытия должны быть `reduceOnly`, а автоматический разворот запрещён.

**Критерий готовности:** на mainnet-субаккаунте с минимальными суммами и ручным подтверждением проверены вход, частичное исполнение, полное исполнение, отмена, отклонение, закрытие и восстановление после таймаута без дублирования ордеров.

## 11. Этап 7. Реализовать reconciliation и восстановление

Биржа является источником истины для фактического состояния. Локальная БД — источник аудита и намерений, но она может расходиться с биржей из-за сбоев.

### 11.1. Сверка при запуске

Перед любыми новыми сигналами:

1. Получить состояние аккаунта.
2. Получить открытые ордера.
3. Получить последние fills.
4. Получить позиции.
5. Сопоставить их с локальными записями.
6. Закрыть или пометить зависшие локальные ордера.
7. Сохранить расхождения.
8. При необъяснимой разнице остаться в `LIVE_PAUSED`.

### 11.2. Периодическая сверка

Во время работы периодически проверяются:

- локальная позиция против биржевой;
- локальные открытые ордера против `openOrders`;
- пропущенные fills;
- баланс и маржа;
- funding и ledger events;
- ордера в статусе `SENT` или `UNKNOWN`;
- разница между рассчитанным и фактическим PnL.

### 11.3. Восстановление после падения

Возможные ситуации:

- ордер сохранён, но не отправлен;
- ордер подписан, но отправка неизвестна;
- ордер принят, но ответ потерян;
- позиция открыта, а бот перезапустился;
- stop-loss существует на бирже, но локальная запись потеряна;
- позиция закрыта вручную через интерфейс Hyperliquid;
- ордер отменён самой биржей.

Для каждой ситуации должен быть отдельный тест и понятная политика восстановления.

**Критерий готовности:** после перезапуска бот сначала восстанавливает фактическое состояние и только потом разрешает работу; необъяснимые расхождения автоматически блокируют новые входы.

## 12. Этап 8. Реализовать risk engine и защитные механизмы

Risk engine должен вызываться непосредственно перед подписанием ордера, даже если сигнал уже прошёл предварительную проверку.

### 12.1. Размер позиции

Базовая логика:

```text
risk_amount = min(
    configured_fixed_risk,
    account_equity × risk_fraction
)

raw_size = risk_amount / distance_to_stop
```

Затем размер ограничивается:

- доступной маржой;
- максимальным номиналом;
- максимальным плечом;
- максимальным размером позиции;
- ликвидностью;
- допустимым проскальзыванием;
- `szDecimals`;
- минимальным номиналом ордера.

Если stop отсутствует, расстояние до него некорректно или размер после округления недопустим — сделка запрещается.

### 12.2. Маржа

Cross margin у Hyperliquid используется по умолчанию, а isolated поддерживается как отдельный режим. См. [Margining](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/margining). Поэтому режим нужно устанавливать и проверять явно, а не предполагать, что аккаунт уже настроен правильно.

Для MVP:

- задавать isolated через соответствующий API-вызов;
- проверять фактический leverage после установки;
- не увеличивать плечо автоматически ради исполнения сигнала;
- не добавлять маржу автоматически для спасения убыточной позиции.

### 12.3. Дневной лимит убытка

В расчёте учитываются:

- реализованный PnL;
- комиссии;
- funding;
- при консервативной настройке — нереализованный PnL.

Funding по perpetual-контрактам Hyperliquid выплачивается каждый час, поэтому его нельзя исключать из учёта результата. См. [Funding](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/funding).

После достижения лимита:

- новые входы запрещаются;
- автоматическое возобновление на следующий день не выполняется без отдельной политики;
- событие записывается в аудит;
- отправляется уведомление.

### 12.4. Защита открытой позиции

После подтверждённого входа:

- создать биржевой reduce-only stop-loss;
- проверить его фактическое наличие;
- при частичном закрытии скорректировать размер защиты;
- при отклонении stop-order немедленно перевести бота в аварийный режим;
- не считать позицию защищённой только потому, что локальный код «создал stop».

### 12.5. Dead man’s switch

Hyperliquid предоставляет `scheduleCancel`: при наступлении заданного времени открытые ордера отменяются. Время должно быть минимум на пять секунд впереди, а число срабатываний ограничено десятью в день. См. [Exchange endpoint — Schedule cancel](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint#schedule-cancel-dead-mans-switch).

Нужен heartbeat-процесс, который периодически продлевает scheduled cancel.

**Важно:** dead man’s switch отменяет открытые ордера, но не закрывает уже открытую позицию.

**Решение 2026-11-17:** при наших типах ордеров (вход — IOC, в книге стоят только защитные стопы) срабатывание `scheduleCancel` сняло бы именно защиту, оставив позицию открытой. Поэтому механизм реализован, но выключен в конфиге (`dead_mans_switch.enabled = false`); включать только при появлении лимитных входов (GTC/ALO). `FULL_KILL` сначала закрывает позицию, затем отменяет ордера — иначе позиция осталась бы без стопа.

Поэтому необходимы разные команды:

- `PAUSE` — запретить новые входы;
- `CANCEL_ALL` — отменить открытые ордера;
- `FLATTEN` — закрыть позиции reduce-only ордерами;
- `FULL_KILL` — запретить новые действия, отменить ордера и потребовать ручного разбора.

### 12.6. Rate limits

Даже для небольшого бота нужен централизованный limiter. У Hyperliquid есть взвешенный IP-лимит 1200 в минуту, отдельные address-based ограничения и лимиты WebSocket. См. [Rate limits and user limits](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits).

Необходимо реализовать:

- token bucket для REST;
- учёт веса разных запросов;
- отдельный резерв для отмены ордеров;
- экспоненциальную задержку для чтения;
- отсутствие слепых повторов торговых действий;
- периодический запрос `userRateLimit`;
- метрики оставшегося лимита.

**Критерий готовности:** ни один сигнал не может обойти risk engine; достижение лимита убытка, устаревание данных или потеря защитного ордера запрещает новые входы.

## 14. Этап 10. Построить feature pipeline и обучающий набор

Только после построения надёжного торгового контура проект переходит к AI.

### 14.1. Признаки первой версии

Используются только воспроизводимые и доступные в реальном времени признаки.

**Цена:**

- доходности за 1, 2, 4, 8, 16 свечей;
- логарифмические доходности;
- положение close внутри диапазона свечи;
- high-low range;
- расстояние до скользящих средних;
- наклон средних;
- разрыв между mark и oracle price.

**Волатильность:**

- realised volatility;
- ATR;
- отношение текущей волатильности к более длинной;
- последовательности расширения и сжатия диапазона.

**Объём и активность:**

- изменение объёма;
- z-score объёма;
- количество сделок;
- средний размер сделки, если данных достаточно.

**Perp-специфика:**

- funding rate;
- изменение open interest;
- совместное движение цены и open interest;
- базис к oracle;
- спред BBO;
- дисбаланс стакана, если он стабильно собирается.

Не нужно добавлять сотни индикаторов. Лучше небольшой набор с понятной версией и отсутствием будущих значений.

**Реализовано (v1):** funding и premium берутся из `fundingHistory` (история есть за весь период свечей). Open interest, mark/oracle и BBO исторически недоступны — они копятся коллектором с момента запуска и войдут в v2, когда истории станет достаточно для обучения. Признаки — чистая функция фиксированного окна (без EMA и другого состояния), поэтому вектор при обучении и в реальном времени совпадает бит в бит.

### 14.2. Target

Например, для горизонта `h` свечей:

```text
UP:
будущая доходность > порог входа + ожидаемые издержки

DOWN:
будущая доходность < -(порог входа + ожидаемые издержки)

FLAT:
остальные случаи
```

В издержки закладываются:

- комиссия;
- ожидаемый спред;
- проскальзывание;
- funding, если горизонт его затрагивает;
- дополнительный запас безопасности.

Порог не должен быть настолько маленьким, что модель обучается в основном на рыночном шуме.

### 14.3. Разбиение данных

Без торгового бэктеста, но обязательно:

- обучающий период — самый ранний;
- validation — более поздний;
- calibration — отдельный более поздний участок;
- финальная проверка классификации — самый поздний участок, который не использовался для выбора модели.

Случайное перемешивание строк запрещено.

Проверяются:

- log loss;
- Brier score;
- калибровка вероятностей;
- precision при рабочем пороге;
- доля сигналов, проходящих порог;
- распределение классов;
- сравнение с простым baseline;
- средняя будущая доходность по прошедшим порог сигналам минус издержки (sanity-check, не симуляция торговли).

Accuracy сама по себе недостаточна: модель может почти всегда предсказывать `FLAT` и выглядеть точной, но быть бесполезной.

### 14.4. Артефакт модели

Вместе с `.cbm` сохраняются:

- упорядоченный список признаков;
- версия кода feature pipeline;
- границы допустимых значений;
- параметры target;
- период обучения;
- конфигурация CatBoost;
- калибратор;
- пороги решения;
- метрики;
- хеши обучающего набора и артефактов.

**Критерий готовности:** по одному и тому же набору входных данных можно воспроизвести идентичный feature vector и прогноз конкретной версии модели.

## 15. Этап 11. Подключить CatBoost к торговой политике

### 15.1. Генерация сигнала

Сигнал создаётся один раз на закрытую свечу:

1. Убедиться, что все необходимые данные получены.
2. Проверить свежесть.
3. Рассчитать признаки.
4. Проверить их на NaN, бесконечности и выход за допустимые границы.
5. Сохранить feature snapshot.
6. Получить вероятности.
7. Сохранить сырой прогноз.
8. Применить торговую политику.
9. Проверить текущую позицию.
10. Передать намерение в risk engine.

При ошибке признаков или модели результат должен быть `HOLD`, а не попытка торговать на частичных данных.

### 15.2. Отказ от сделки

Недостаточно выбирать класс с максимальной вероятностью. Нужны условия:

```text
p_buy >= минимальный порог
p_buy - p_sell >= минимальный отрыв
ожидаемое преимущество > издержек + запаса
данные свежие
risk engine разрешает сделку
```

Аналогично для short. В остальных случаях — `HOLD`.

### 15.3. Поведение открытой позиции

Для MVP:

- новый сигнал в том же направлении не увеличивает позицию;
- противоположный сигнал может закрыть позицию, но не развернуть её;
- новый вход после выхода возможен только на следующей допустимой свече;
- stop-loss и time-exit имеют приоритет над сигналом модели.

### 15.4. Управление версиями

- Только одна активная версия.
- Новая модель сначала работает в shadow.
- Смена версии фиксируется в аудите.
- Предыдущая версия доступна для отката.
- Автоматическое переобучение не активирует модель самостоятельно.
- Нельзя менять модель посреди обработки одного сигнала.

### 15.5. Pydantic AI

Pydantic AI подключается только после стабильной торговли.

Допустимые задачи:

- человекочитаемое объяснение уже принятого решения;
- ежедневный отчёт;
- поиск аномалий в журнале;
- помощь оператору;
- суммирование новостей как отдельного эксперимента.

Pydantic AI не должен:

- изменять вероятности CatBoost;
- самостоятельно менять лимиты;
- выбирать размер позиции;
- вызывать `place_order`;
- отменять kill switch.

**Критерий готовности:** каждое решение объясняется структурированными данными — вероятностями, порогами, позицией и риск-проверками, а не только текстовым объяснением LLM.

## 16. Этап 12. Проверка без исторического торгового бэктеста

### 16.1. Модульные тесты

Обязательно проверить:

- округление цены и размера;
- asset ID;
- nonce;
- генерацию и уникальность `cloid`;
- расчёт размера позиции;
- дневной лимит убытка;
- запрет превышения номинала;
- reduce-only логику;
- переходы состояний ордера;
- дедупликацию fills;
- обработку snapshot после reconnect;
- запрет сигнала на незакрытой свече;
- обработку неизвестного ответа SDK;
- восстановление после рестарта.

### 16.2. Минимальный mainnet (вместо testnet)

Проверяется техническая корректность на отдельном субаккаунте с минимальным балансом: каждый ордер ~10–15 USDC и подтверждается вручную. Это не оценка доходности.

Сценарии:

1. Открыть long.
2. Получить fill.
3. Проверить позицию.
4. Проверить защитный stop.
5. Частично закрыть.
6. Полностью закрыть.
7. Открыть short.
8. Отменить resting-ордер.
9. Получить намеренный rejection.
10. Проверить reduce-only rejection.
11. Проверить ограничение размера.
12. Обновить leverage.
13. Проверить scheduleCancel.
14. Перезапустить бота с открытой позицией.
15. Сверить все события с PostgreSQL.

### 16.3. Тестирование сбоев

Необходимо искусственно воспроизвести:

- потерю соединения до отправки;
- потерю соединения после отправки, но до ответа;
- задержку ответа;
- дубликат WebSocket-события;
- пропуск WebSocket-события;
- перезапуск после создания ордера;
- перезапуск после fill;
- недоступность PostgreSQL;
- недоступность Logfire;
- отказ модели;
- неверный feature vector;
- устаревшие рыночные данные;
- резкое изменение спреда;
- ручное закрытие позиции через интерфейс биржи;
- срабатывание dead man’s switch;
- попытку запустить второй trader-процесс.

Главный критерий: **ни один сбой не должен приводить к слепому повтору ордера**.

### 16.4. Mainnet shadow

Бот получает реальные mainnet-данные и строит прогнозы, но не подписывает ордера.

Для каждого сигнала сохраняются:

- время;
- вероятности;
- feature snapshot;
- желаемое действие;
- актуальные bid/ask;
- спред;
- цена, по которой реально можно было бы начать исполнение;
- результат после наступления горизонта;
- причины отказа risk engine.

Оцениваются:

- стабильность признаков;
- частота сигналов;
- распределение вероятностей;
- калибровка по мере накопления результатов;
- задержки;
- количество отказов;
- расхождение ожидаемых и наблюдаемых рыночных условий;
- операционная стабильность.

Shadow-режим не учитывает реальное влияние ордера на исполнение и все нюансы fills, поэтому следующий этап всё равно необходим.

## 17. Этап 13. Минимальный реальный запуск

### 17.1. Подготовка

- Отдельный субаккаунт с ограниченным капиталом.
- Отдельный API-кошелёк.
- Минимальный размер позиции.
- Минимальное плечо.
- Жёсткий дневной лимит.
- Отключённый автоматический рестарт торговли.
- Уведомления оператору.
- Проверенный kill switch.
- Проверенное восстановление БД.
- Ручная процедура аварийного закрытия.

### 17.2. Ступень 1 — ручное подтверждение

Модель создаёт сигнал, risk engine рассчитывает ордер, но отправка происходит только после подтверждения оператором.

Проверяется:

- правильно ли рассчитан размер;
- не меняется ли рынок до отправки;
- корректно ли выставляется stop;
- совпадают ли fills и комиссии;
- правильно ли рассчитывается результат.

### 17.3. Ступень 2 — автоматическое исполнение с минимальными лимитами

Включать только после успешного ручного этапа.

Бот работает с:

- одной позицией;
- минимальным размером;
- запретом увеличения позиции;
- запретом автоматического разворота;
- автоматическим pause при любой необъяснимой разнице с биржей.

### 17.4. Ступень 3 — постепенное расширение

Увеличивать лимиты отдельными небольшими изменениями, а не одновременно:

- размер позиции;
- число сделок;
- число рынков;
- сложность исполнения;
- частоту сигналов.

Нельзя масштабировать капитал только потому, что несколько сделок оказались прибыльными. Сначала должны быть подтверждены:

- отсутствие дублей;
- отсутствие неучтённых fills;
- корректное восстановление;
- стабильное исполнение;
- контролируемые издержки;
- достаточное количество наблюдений;
- приемлемая просадка;
- отсутствие деградации модели.

## 18. Этап 14. Эксплуатация и дальнейшее развитие

### 18.1. Ежедневный контроль

- Сравнение локального и биржевого состояния.
- Realised/unrealised PnL.
- Комиссии.
- Funding.
- Проскальзывание.
- Отклонённые ордера.
- Количество сигналов.
- Доля `HOLD`.
- Просроченные `UNKNOWN`.
- Пропуски данных.
- Срабатывания лимитов.
- Версия модели.
- Распределение признаков и вероятностей.

### 18.2. Деплой новой версии

Для trader-процесса нельзя использовать обычный rolling deployment с двумя одновременно активными экземплярами.

Правильная последовательность:

1. Запретить новые входы.
2. Дождаться завершения неопределённых операций или разобрать их.
3. Проверить биржевые защитные ордера.
4. Остановить старый trader.
5. Запустить новый.
6. Выполнить reconciliation.
7. Проверить здоровье.
8. Разрешить работу вручную.

### 18.3. Переобучение

- Запускать отдельно от торговли.
- Создавать новую версию, не перезаписывать старую.
- Проверять на новом временном участке.
- Отправлять в shadow.
- Активировать вручную.
- Сохранять возможность отката.
- Не обучать на непроверенных или неполных live-данных.

## 22. Главный принцип

**CatBoost не должен быть первым работающим компонентом.** Сначала необходим бот, который безопасно исполняет простой ручной сигнал, переживает таймауты и перезапуск, не создаёт дубли и умеет остановиться. Только после этого имеет смысл оценивать качество AI-прогноза.
